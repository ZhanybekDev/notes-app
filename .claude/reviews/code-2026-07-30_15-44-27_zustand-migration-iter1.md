## Critical Findings

### C1. `notesStore.error` не сбрасывается никогда — баннер ошибки переживает и успешную загрузку, и уход со страницы

- **Dimension:** D1 Correctness / D6 Blast radius
- **Severity:** Critical
- **Where:** `frontend/src/stores/notesStore.js:18` (объявление) и строки `54, 91, 101, 110, 123, 134` (шесть присваиваний)
- **Problem:** `error` устанавливается в шести местах и **не очищается ни в одном**. `grep "error"` по файлу
  даёт только `error: null` в начальном состоянии и шесть `set({ error: err.message })`. Успешный
  `load()` не трогает поле.

  Два следствия, второе — регрессия относительно поведения до переезда:

  1. Разовый сбой сети показывает баннер, и он остаётся навсегда: следующая успешная загрузка
     рендерит свежий список **под** сообщением об ошибке. Пользователь видит «offline» над
     работающими данными.
  2. До переезда `error` был локальным состоянием страницы
     (`git show 8ed11d8:frontend/src/pages/Notes.jsx` — `const [error, setError] = useState(null)` на
     строке 23), то есть умирал вместе с размонтированием. Теперь он в синглтоне: маршрут
     `/notes → /calendar → /notes` возвращает пользователя к устаревшему баннеру.

- **Evidence:**
  ```js
  // notesStore.js — единственные упоминания error
  error: null,                        // :18 initial
  set({ error: err.message });        // :54  load
  set({ error: err.message });        // :91  save
  set({ error: err.message });        // :101 remove
  ...
  ```
  Для сравнения — `accountStore.js` так не делает: `load` (`:31`), `patch` (`:49`) и `unlink` (`:63`)
  начинаются с `error: null`, поэтому там состояние самовосстанавливается.

- **Suggested fix:** сбрасывать `error` в начале каждого действия (как в `accountStore`), либо
  очищать его при успешном `load`. Плюс тест: сбой → успешная загрузка → `error === null`; и
  ремоунт страницы после сбоя не показывает баннер.

### C2. `initTheme()` и `initLang()` не покрыты ни одним тестом — критерий «до первого рендера» не проверяется

- **Dimension:** D11 Test coverage / D1 Correctness
- **Severity:** Critical
- **Where:** `frontend/src/theme.js:23-35`, `frontend/src/i18n.jsx:374-380`; вызовы — только
  `main.jsx:11-12`
- **Problem:** `grep -rn "initTheme\|initLang"` по `frontend/src` находит их лишь в определении,
  в `main.jsx` и в **комментарии** внутри `theme.test.js`. Ни один тест их не вызывает.

  Это ровно та функция, в которой живёт риск, признанный планом главным для фазы 4: `subscribe`
  срабатывает только на изменение, поэтому первое применение обязано быть явным. Тесты
  `theme.test.js` зовут `applyTheme(...)` напрямую и потому обходят обе функции целиком: если
  однажды из `initTheme` убрать первый `applyTheme(...)`, оставив подписку, **все тесты останутся
  зелёными**, а пользователь с тёмной темой получит светлый первый кадр. Симметрично для
  `<html lang>` — атрибут остался бы английским до первого переключения языка.

  Отдельно не покрыт `matchMedia`-слушатель: смена системной темы при `theme === 'system'`.

- **Suggested fix:** тест на `initTheme()` — стор с `theme: 'dark'`, вызов, проверка
  `data-theme="dark"` **без** какого-либо изменения состояния; затем `setTheme('light')` и проверка,
  что подписка сработала. Тест на `initLang()` — `<html lang>` выставлен до изменений и меняется
  после `setLang('ru')`. Тест на `matchMedia`: при `system` смена системной темы перекрашивает.
