## Findings by Dimension

### D1. Correctness / D3. Performance

**C6 — заметки из полос запаса вечно занимают квоту прохода и вытесняют настоящую работу.**

`backend/app/reminders.py:53-79` в связке с `_in_range` (`reminders.py:66`)

Отбор кандидатов идёт по **датам** с запасом в сутки с каждой стороны, а отсечка — по
**вычисленному моменту**:

```python
earliest = (now - BACKFILL_WINDOW).date() - timedelta(days=1)
latest = (now + MATERIALIZE_HORIZON).date() + timedelta(days=1)
...
        .order_by(Note.note_date, Note.id)
        .limit(RECONCILE_LIMIT)
```

```python
def _in_range(scheduled_for: datetime, now: datetime) -> bool:
    return now - BACKFILL_WINDOW <= scheduled_for <= now + MATERIALIZE_HORIZON
```

Запас в сутки существует потому, что таймзона пользователя может сдвинуть момент через границу
даты. Но он же впускает заметки, которые `_in_range` отвергнет **всегда**, при любой таймзоне.
А `NOT EXISTS` для них никогда не перестанет срабатывать — строка не создаётся, значит на
следующем проходе заметка снова кандидат.

Арифметика на конкретных числах, `now = 2026-08-01 06:00 UTC`:

| шаг | значение |
|---|---|
| `earliest` | `(2026-07-31 06:00).date() − 1 день` = **2026-07-30** |
| заметка с `note_date = 2026-07-30`, UTC, 09:00 | `scheduled_for = 2026-07-30 09:00` |
| `_in_range`: `now − 24ч` | `2026-07-31 06:00` |
| `2026-07-31 06:00 <= 2026-07-30 09:00` | **нет** → отвергнута |
| строка в `reminders` | не создана → `NOT EXISTS` истинно → снова кандидат |

Отдельно усугубляет **сортировка**: `order_by(Note.note_date, Note.id)` по возрастанию ставит
именно самые старые заметки в начало — то есть те, которые гарантированно будут отвергнуты,
занимают первые слоты каждого прохода.

Условие срыва: если заметок в двух суточных полосах запаса суммарно больше `RECONCILE_LIMIT`
(500) по всем пользователям с включёнными уведомлениями — материализация **никогда не доходит до
тех, что реально наступили**. Напоминания просто перестают отправляться, молча.

Смягчает то, что заметка выпадает из полосы за сутки — набор не бессрочный, а обновляющийся.
Но он воспроизводится каждый день, и порог в 500 достигается 500 пользователями с одной
позавчерашней заметкой на каждого.

Существующие тесты границ окна мимо: `test_skips_note_older_than_backfill_window` берёт
`2026-07-20` — это вне фильтра дат целиком, полоса запаса не затрагивается.

**Suggested fix:** отсечь в SQL то, что `_in_range` заведомо отвергнет. Запас в сутки избыточен —
достаточно реального размаха смещений UTC (`MAX_UTC_OFFSET_SPAN`, уже объявлен в этом же модуле):
`earliest = (now - BACKFILL_WINDOW - MAX_UTC_OFFSET_SPAN).date()`, симметрично для `latest`.
Остаточный набор станет узким и не будет доминировать в квоте. Плюс тест на заметку, датированную
в полосе запаса: она не должна вытеснять наступившую.

## Minor Findings

  `update.get("update_id")`, которое может быть `None`. Тогда все безымянные апдейты делят один
  счётчик, а на пути пропуска `if isinstance(update_id, int)` не даёт продвинуть offset — счётчик

  сказано.

## Blast Radius Analysis

C6 живёт целиком в `materialize_due` и проявляется как **тихая остановка отправки** — самый
неприятный режим отказа для этой фичи: ни ошибки, ни записи в логе, напоминания просто перестают
приходить. Ни данные, ни гарантия exactly-once не страдают: `UNIQUE (note_id, note_date)` держит
своё независимо, дублей не будет ни при каком раскладе. API, аутентификация и работа с заметками
не затронуты.

Порог — свыше 500 заметок в суточных полосах запаса по всем пользователям сразу. На демо-данных
(5 заметок) недостижим.
