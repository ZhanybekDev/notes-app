## Findings by Dimension

### D3. Performance

**C5 — `_eligible_notes` остался единственным неограниченным сканом, и фикс C3 навесил на него неограниченный `IN`.**

`backend/app/reminders.py:45-59` и `83-88`

```python
def _eligible_notes(db: Session, now: datetime) -> list[tuple[Note, User]]:
    ...
    return (
        db.query(Note, User)
        .join(User, Note.user_id == User.id)
        .filter(...)
        .all()            # ни limit, ни ordering
    )
```

```python
    existing = {
        (row.note_id, row.note_date): row
        for row in db.query(Reminder)
        .filter(Reminder.note_id.in_([note.id for note, _ in candidates]))   # длина = len(candidates)
        .all()
    }
```

Два отдельных дефекта, наложившихся друг на друга:

1. **Неполнота фикса C4.** Iteration 1 требовала ограничить сканы, выполняющиеся каждые 30 секунд. `resync_pending` и `cancel_stale` ограничены (`RECONCILE_LIMIT`, фильтр по горизонту), а `_eligible_notes` — нет, хотя это самая тяжёлая из трёх выборок: join `notes × users` по 72-часовому окну дат, целиком в память, каждый тик. Ограничение применено к двум запросам из трёх без объяснения, почему третий исключён.

2. **Фикс C3 внёс новый риск.** До фикса существующая строка искалась по одной (`one_or_none()` на заметку) — плохо по числу запросов, но с константным числом bind-параметров. Теперь список `note_id` целиком уходит в `IN`. У Postgres потолок 65535 bind-параметров на выражение, и при превышении это не деградация, а жёсткая ошибка `too many arguments`. То есть обмен «много запросов → один большой» перенёс проблему из плоскости скорости в плоскость отказа.

Практическая шкала: 1000 пользователей × 3 датированные заметки в окне = 3000 строк в память и 3000-элементный `IN` каждые 30 секунд. Для тестового задания недостижимо, но именно это ревью и требует замечать.

**Suggested fix:** ограничить `_eligible_notes` тем же `RECONCILE_LIMIT` с детерминированным `order_by` (например `Note.note_date, Note.id`), чтобы непоместившееся забирал следующий проход — ровно так, как уже сделано в двух других проходах. `IN` тогда ограничен автоматически.
