# Plan: Переезд фронтенда на Zustand

**Goal:** Глобальное состояние фронтенда живёт в сторах Zustand, а не в четырнадцати `useState`
страницы и одном Context: настройки аккаунта — одна копия на приложение вместо двух независимых,
сессия реактивна, localStorage трогают только сторы.

**Context:** Сейчас в `frontend/` нет ни одной state-библиотеки: `Notes.jsx` держит 14 `useState`
(`grep -c "= useState"`, строки 12–26), `Settings.jsx` — 11, единственный Context — `LangContext`. Две конкретные вещи из этого ломаются
уже сегодня: настройки аккаунта загружаются двумя независимыми копиями кода с собственной
обработкой ошибок (`Notes.jsx:56-71` и `Settings.jsx:63-78`), и каждый заход на страницу начинается
с пустого плейсхолдера, потому что делить загруженное между страницами негде; `isAuthenticated()`
(`App.jsx:16`) читает localStorage на рендере, поэтому разлогин в соседней вкладке текущая никак не
замечает. Research
(`.claude/research/zustand-migration.md`) подтвердил: zustand 5.0.14 (MIT, ноль зависимостей, peer
`react >=18`) встаёт на React 18.3.1 без конфликтов.

**Total estimate:** 4–5.5 часов / 1–2 сессии Claude Code

> Оценка поднята с первоначальных 2.5–4 после пяти проходов ревью: в план добавились свои
> `PersistStorage` в двух вариантах (одиночный и fan-out), тесты гидратации с `persist.rehydrate()`,
> тест на счётчик запросов, синхронное применение темы и языка до рендера, правки
> `docs/architecture.md` в трёх фазах, `SUBMISSION.md` и два тестовых файла с нуля — `Notes.test.jsx`
> и `App.test.jsx`, потому что у обоих файлов сегодня нет ни одного теста. Требований стало вдвое
> больше, и старая цифра осталась бы от плана, которого уже нет.

## Phase 1: Заметки живут в сторе

**Estimate:** 1.5–2 часа

**What changes:**
- `frontend/package.json` + `package-lock.json` — `zustand: ^5.0.14` в `dependencies`. Ставить через
  контейнер (`docker compose exec frontend npm install zustand`), потому что локального
  `node_modules` нет, а в compose он анонимным volume (`/app/node_modules`) перекрывает смонтированный
  каталог — после установки нужен `docker compose build frontend`, иначе импорт упадёт у всех, кто
  поднимет стек заново.

  > **Проверено на исполнении: одной пересборки образа мало.** `npm install` внутри контейнера ломает
  > дерево `node_modules` известным багом npm с опциональными нативными зависимостями rollup
  > (`Cannot find module @rollup/rollup-linux-arm64-musl`), а `docker compose up --force-recreate`
  > переиспользует **тот же** анонимный volume и поднимает контейнер на битом дереве. Рабочая
  > последовательность: `docker compose build frontend` →
  > `docker compose up -d --force-recreate --renew-anon-volumes frontend`. Последний флаг и есть
  > ключевой: он выбрасывает анонимный volume и заполняет его заново из образа.
- `frontend/src/stores/notesStore.js` — новый. Состояние: `items`, `total`, `tags`, `selected`,
  `creating`, `search`, `activeTag`, `view`, `offset`, `bulkMode`, `selectedIds`, `error`.
  Действия: `load(offset, append)`, `loadMore()`, `save(data)`, `remove(id)`, `setPin(note, pin)`,
  `setArchive(note, archive)`, `bulkDelete(ids)`, `setSearch`, `setActiveTag`, `setView`,
  `select(note)`, `startCreating()`, `toggleBulk()`, `toggleSelect(id)`, `selectAll()`. Асинхронные
  действия зовут `api.*` и сами перезагружают список после мутации — инвалидация ручная, это цена
  того, что серверные данные лежат в client-state сторе.

  > **Перезагрузка при смене фильтра живёт ровно в одном месте — в действиях.** Сегодня она держится
  > на цепочке `useCallback([search, activeTag, view])` → `useEffect([load])` (`Notes.jsx:31-54`),
  > то есть на идентичности функции. При переезде эта цепочка исчезает, и здесь два симметричных
  > способа промахнуться: оставить страницу без перезагрузки (фильтр меняется, список нет) или
  > оставить `useEffect` **и** перезагрузку внутри `setSearch` — тогда каждое нажатие клавиши даёт
  > два запроса вместо одного. Договорённость: `setSearch`, `setActiveTag`, `setView` сами зовут
  > `load(0, false)`; у страницы остаётся единственный `useEffect` — начальная загрузка при монтаже.
  > Паритет поведения: дебаунса поиска нет сейчас и не появляется здесь — это отдельная задача.

  > **Стор остаётся headless.** `window.confirm` перед bulk-удалением (`Notes.jsx:151`) и любые
  > другие обращения к `window` остаются в компоненте: действие стора принимает уже подтверждённый
  > список id. Иначе юнит-тест стора нельзя написать без подмены глобалов, а весь смысл выноса
  > логики в стор — в том, что он тестируется без React и без DOM.

  > **Сеть зовётся через объект `api`, а не через выдернутую ссылку.** Сеть мокают только два файла
  > из семи — `pages/Settings.test.jsx` и `hooks/useTelegramLink.test.js`, 26 тестов из 52 — и оба
  > делают это через `vi.spyOn(api, 'метод')` (`Settings.test.jsx:46`). Остальные пять файлов до
  > сети не доходят вовсе, поэтому весь риск сосредоточен в этих двух и в новых тестах сторов.
  > Стор, написавший `const { listNotes } = api` на уровне модуля, забирает ссылку до
  > установки спая, и перехват молча перестаёт работать: тест не падает, он просто ходит в
  > настоящий `fetch`. Правило одно на все четыре стора.
- `frontend/src/stores/index.js` — новый. `resetStores()`: для каждого стора
  `store.setState(store.getInitialState(), true)` — API проверен по официальному testing-гайду
  zustand (`pmndrs/zustand → docs/learn/guides/testing.md`; у этого проекта свой каталог `docs/`,
  поэтому внешние ссылки всегда с префиксом репозитория). **Каждая следующая фаза дописывает сюда свой стор в том же коммите, что и создаёт его.**
  Забытая регистрация ничего не ломает громко: тесты продолжают проходить, просто состояние нового
  стора течёт между ними, и однажды падает тест, который сам по себе верен.
- `frontend/src/test/setup.js` — `resetStores()` в существующий `afterEach` **строго до**
  `localStorage.clear()`. Стор — синглтон на процесс тестов, без сброса состояние течёт между
  тестами; порядок важен, потому что сброс persist-стора (фазы 3–4) сам пишет в localStorage, и
  вызов после `clear()` оставил бы мусор следующему тесту.
- `docs/architecture.md` — три места: `:29` (таблица сервисов, «React 18, Vite, React Router»),
  раздел «Frontend packages» — **и список модулей, и mermaid-граф внутри него**: у графа появляется
  узел `STORES["stores/*"]` с рёбрами `PAGES --> STORES` и `STORES --> API`, — плюс `stores/` в
  дерево «Frontend layout» (`:207`–`:221`). Документ перечисляет пакеты и модули поимённо, поэтому
  новый каталог обязан появиться там в той же фазе, что и в коде. Запись `stores/` в дереве ведётся в
  том же стиле, что `components/` — с именами внутри, — и **каждая фаза дописывает туда свой стор**:
  иначе дерево навсегда останется с одним `notesStore`, как и реестр в `stores/index.js`.

  > Существующие рёбра `PAGES --> API` и `COMP --> API` остаются верными и не удаляются: `Login`,
  > `Register` и `Calendar` продолжают звать `api` напрямую (календарь вне scope, формы входа держат
  > состояние локально). Граф получает новый слой, а не заменяет старые связи — проверено по
  > импортам всех пяти страниц.
- `frontend/src/pages/Notes.jsx` — потребитель стора. Локальными остаются только `searchRef` и
  `editorRef` (DOM-ссылки) и подписка `registerAction`. `PAGE_SIZE` переезжает в стор.
- `frontend/src/stores/notesStore.test.js` — новый.
- `frontend/src/pages/Notes.test.jsx` — **новый файл, и это не деталь оформления.** У `Notes.jsx`
  сегодня нет ни одного теста: тестовая база из 52 тестов покрывает `NoteEditor`, `TagFilter`,
  `Settings`, `useTelegramLink`, `i18n`, `theme` и `reminderStatus` — то есть всё, кроме самой
  большой страницы приложения, которую эта фаза и переписывает целиком (272 строки; базовая линия —
  52 теста, см. assumption 15). Пока файла нет,
  критерий «работает ровно как до переезда» проверяется только руками, а «ни один тест не удалён»
  ничего не защищает: удалять нечего. Минимум, который должен появиться: рендер списка, выбор
  заметки, поиск, переключение вкладки, bulk-режим со счётчиком запросов.

**Acceptance criteria:**
- [ ] Селекторы подписываются по полям; ни один селектор не возвращает свежесозданный объект без
      `useShallow` — иначе v5 даёт не лишний ререндер, а `Maximum update depth exceeded`
- [ ] Список, поиск, фильтр по тегу, вкладки active/archived, «загрузить ещё», bulk-режим и
      удаление выделенного работают ровно как до переезда
- [ ] После create / update / delete / pin / archive / bulk-delete список перезагружается — стор
      сам инвалидирует, компонент про это не знает
- [ ] Ошибка любого действия садится в `error` стора и рендерится там же, где рендерилась
- [ ] Смена поиска, тега или вкладки даёт **ровно один** запрос списка — не ноль (забыли
      перезагрузку) и не два (перезагрузка и в действии, и в `useEffect`)
- [ ] `docker compose build frontend` выполнен, `npm run dev` в контейнере поднимается
- [ ] `zustand: ^5.0.14` зафиксирован **в `package.json` и в `package-lock.json`** — `git diff`
      показывает оба файла. Установка только внутри контейнера, не доехавшая до манифеста, — это
      работающий у автора и падающий у всех остальных импорт
- [ ] **Изоляция тестов доказана, а не заявлена:** тест, который мутирует стор, и следующий за ним,
      который видит начальное состояние. Четыре требования плана опираются на `resetStores()`
      (порядок до `localStorage.clear()`, пополнение реестра в каждой фазе), и ни одно из них не
      проверяется, если сам сброс молча не работает
- [ ] Тесты и линт гоняются в контейнере (`docker compose exec frontend npm run test` / `… lint`) —
      локального `node_modules` нет, снаружи команды просто не запустятся
- [ ] Тесты стора и **новый** `Notes.test.jsx` проходят; линт зелёный. Слова «обновить тесты
      страницы» здесь неприменимы: обновлять нечего, файл создаётся с нуля
- [ ] `docs/architecture.md` упоминает `zustand` и `stores/` — документ не отстаёт от кода
- [ ] **Ни один существующий тест не удалён ради зелёного прогона.** Базовая линия — **52** теста в
      7 файлах (6 + 3 + 8 + 5 + 18 + 9 + 3, подсчёт `grep -cE "^[[:space:]]*it\("`); переписать тест
      под новый способ монтирования можно, выбросить неудобный — нет.
      Правило действует во всех четырёх фазах: миграция состояния — классическое место, где тесты
      тихо исчезают вместе с поведением, которое они держали

**Implementation outline:**
1. Установка zustand в контейнере + `docker compose build frontend`.
2. `stores/notesStore.js` целиком с действиями и тесты к нему — до того, как трогать страницу.
3. `stores/index.js` + `resetStores()` в `test/setup.js`.
4. `Notes.jsx` переводится на селекторы; уезжают **12** `useState` (`items` … `error`, строки 12–23)
   и `load`; остаётся один `useEffect` — начальная загрузка. Ещё два — `reminderPrefs` и
   `reminderPrefsFailed` (строки 25–26) — уходят в фазе 2 вместе с настройками, а не забыты здесь.
5. `docs/architecture.md` — `zustand` и `stores/`.
6. Self-review + `docker compose exec frontend npm run test` + `… npm run lint`.

**Test strategy:**
- Unit: изоляция — один тест мутирует стор, следующий читает `getInitialState()` и видит чистое
  состояние; это проверка самого `resetStores()`, а не поведения страницы.
- Unit: стор напрямую, без React — `load` кладёт items/total/tags; `append` дописывает, а не
  затирает; мутация зовёт `api` и перезагружает список; ошибка `api` садится в `error`;
  `toggleSelect` не мутирует прежний `Set`; `setSearch` / `setActiveTag` / `setView` дают ровно один
  `listNotes` на вызов.
- Integration: набор трёх символов в поле поиска даёт три запроса, а не шесть — тест на счётчик

- Integration: `Notes.jsx` через Testing Library со `vi.spyOn(api, …)` — как уже написаны тесты в
  проекте.
- Manual: `/notes` в браузере — поиск, теги, пагинация, bulk-удаление.

## Phase 2: Настройки аккаунта — один источник на всё приложение

**Estimate:** 0.5–1 час

**What changes:**
- `frontend/src/stores/accountStore.js` — новый. `prefs`, `status` (`idle`/`loading`/`ready`/`error`),
  `error`, `saved`. Действия: `load()`, `patch(patch)`, `unlink()`, `setPrefs(next)` для внешнего
  источника.

  > **`load()` дедуплицирует параллельные вызовы, но не отменяет перезапрос при заходе на
  > страницу.** Настройки меняются не только из веба: `/pause` и `/resume` в боте пишут
  > `notifications_enabled` прямо в БД (`backend/app/bot_commands.py:192`). Кеш «загрузили один раз
  > и больше не спрашиваем» показывал бы «Напоминания: включены» после того, как пользователь
  > заглушил их из Telegram, — молча и до перезагрузки вкладки. Поэтому `load()` держит один
  > in-flight запрос на всех подписчиков, отдаёт кешированное значение сразу и перезапрашивает в
  > фоне при монтировании страницы.

  > **Честно про выигрыш: число запросов почти не меняется.** Роутер рендерит ровно один маршрут
  > (`App.jsx:98-106`), поэтому `/notes` и `/settings` никогда не смонтированы одновременно, а
  > перезапрос при монтаже оставляет по запросу на каждый заход — как и сейчас. Дедупликация
  > срабатывает только на параллельных подписчиках одного экрана. Фаза окупается другим: одна копия
  > состояния вместо двух наборов `useState` с двумя обработками ошибок, мгновенный рендер из кеша
  > вместо плейсхолдера `…` при каждом заходе (`Settings.jsx:170`) и общий источник для подсказки о
  > напоминании на `/notes`. Формулировка «два запроса схлопываются в один» была бы неправдой, и
  > критерий на неё проверить нельзя.
- `frontend/src/pages/Settings.jsx` — `prefs`/`prefsError`/`prefsSaved` уезжают в стор. Локальными
  остаются черновики форм: `timeDraft`, пароли, `deletePw` — это состояние ввода, а не приложения.

  > **Таймер, гасящий плашку «сохранено», остаётся в компоненте** (`Settings.jsx:108-112`). В сторе
  > он превратился бы в `setTimeout`, который переживает и размонтирование страницы, и
  > `resetStores()` — тот сбрасывает состояние, но не отменяет уже запущенные таймеры, и тест начал
  > бы получать чужой `saved: false` посреди своего сценария. Стор хранит факт `saved`, время жизни
  > плашки — забота экрана.
- `frontend/src/pages/Notes.jsx` — `reminderPrefs` и `reminderPrefsFailed` берутся из того же стора:
  `prefs` напрямую, `reminderPrefsFailed` выводится из `status === 'error'`. Разница между «ещё
  грузится» (`null`) и «не удалось» сегодня несёт смысл — подсказка у поля даты в первом случае
  молчит, во втором объясняет, — и её нельзя схлопнуть в одно поле.
- `frontend/src/hooks/useTelegramLink.js` — **не меняется, и это проверяемое требование, а не
  оговорка.** Пункт стоял в списке правок и в той же строке утверждал, что хук не меняется —
  противоречие, которое стоило бы ship-it лишнего рефакторинга. Фактически шов уже на месте:
  `onLinked` — колбэк, который передаёт сам `Settings.jsx` (`:100-101`), а хук только вызывает его
  (`useTelegramLink.js:41`). Достаточно передать `setPrefs` вместо локального сеттера — правка целиком
  внутри `Settings.jsx`, уже перечисленного выше.

  > Почему это важно назвать: увидев файл в списке, исполнитель «научит хук писать в стор», то есть
  > импортирует `accountStore` внутрь хука. Это привяжет универсальный хук к конкретному стору и
  > создаст второй путь записи рядом с колбэком — при живом первом. Восемь тестов хука сейчас зелёные
  > именно потому, что он ничего не знает о том, куда уходит результат.
- `frontend/src/pages/Settings.test.jsx` — обновить под стор.
- `frontend/src/stores/accountStore.test.js` — новый.

**Acceptance criteria:**
- [ ] Два подписчика, смонтированных в одном тике, дают один `GET /account/settings` — дедупликация
      работает там, где она вообще применима
- [ ] Повторный заход на `/settings` рендерит настройки сразу из кеша, без плашки `…` — состояние
      переживает уход со страницы, чего сейчас нет
- [ ] Заход на `/settings` после `/pause` в боте показывает актуальное «выключено»: кеш отдаётся
      сразу, но перезапрос идёт — стор не превращает настройки в вечно свежие по мнению вкладки
- [ ] PATCH таймзоны, времени и тумблера уведомлений обновляет обе страницы без перезагрузки
- [ ] Черновик времени по-прежнему не затирается при PATCH другого поля (поведение из
      `Settings.jsx:88` сохраняется)
- [ ] Плашка «сохранено» гаснет через 2.5 с и не залипает
- [ ] Привязка Telegram через `useTelegramLink` обновляет стор, `/notes` подхватывает подсказку о
      напоминании без перезагрузки страницы
- [ ] Отвязка чистит `telegram_linked`/`telegram_username` в сторе
- [ ] `git diff --stat` по фазе **не содержит** `hooks/useTelegramLink.js` — шов остался колбэком,
      хук не узнал про сторы; его восемь тестов не тронуты
- [ ] `npm run test` и `npm run lint` зелёные

**Implementation outline:**
1. `stores/accountStore.js` + тесты стора.
2. `Settings.jsx` на стор, черновики форм оставить локальными.
3. `Notes.jsx` — `reminderPrefs` из стора, свой `useEffect` с фетчем удалить.
4. `useTelegramLink` → `setPrefs`; проверить, что тесты хука не поехали.
5. Self-review + тесты + линт.

## Phase 3: Сессия реактивна

**Estimate:** 0.5–1 час

**What changes:**
- `frontend/src/stores/sessionStore.js` — новый, с `persist`-middleware на ключ `notes_token`.
  `token`, `isAuthenticated` как селектор, `login(token)`, `logout()`. Подписка на событие `storage`
  окна: вкладка применяет то значение, которое пришло, в обе стороны — пустое разлогинивает, новый
  токен логинит.

  > **Симметрия здесь не украшение.** Слушать только опустевший ключ означает: вышел в одной
  > вкладке — вышли обе, вошёл в одной — вторая осталась на `/login` и покажет форму входа
  > пользователю, который уже вошёл. Это выглядит как баг ровно потому, что половина механизма
  > работает. Обработка одного события в обе стороны — та же строка кода.

  > **`storage` пишется вручную, `createJSONStorage` брать нельзя.** Дефолтное хранилище persist —
  > `createJSONStorage(() => localStorage)`, а оно кладёт не значение, а конверт
  > `{"state":{…},"version":0}` через `JSON.stringify` (документация persist, раздел про `storage`).
  > Сейчас в `notes_token` лежит голый JWT, то есть **не валидный JSON**: `JSON.parse` на нём
  > бросает, гидратация проваливается, и обновление приложения молча разлогинивает всех, у кого
  > была живая сессия. Поэтому у стора свой `PersistStorage`: пишет и читает голую строку, а на
  > чтении принимает и легаси-значение, и собственный формат. Здесь адаптер простой: одно поле —
  > один ключ.

  > **Адаптер обязан не бросать — иначе белый экран вместо приложения.** Проверено, как обстоит дело
  > сейчас: `localStorage` обёрнут в try/catch в **четырёх** местах двух файлов (`i18n.jsx:326`,
  > `:362`, `Settings.jsx:26`, `:55`), а `theme.js:5,10` и `auth.js:4,8,12` не защищены вовсе. То
  > есть пользователь с заблокированным хранилищем (приватный режим Safari, корпоративная политика,
  > отключённые данные сайтов) сегодня получает работающее приложение — просто без запомненной темы.
  > После переезда **весь** доступ к хранилищу идёт через два адаптера, и их устойчивость решает всё:
  > `getItem` бросает на гидратации, гидратация случается при импорте модуля — приложение не
  > отрендерится вообще. Поэтому оба адаптера (здесь и в фазе 4) ловят исключения на чтении, записи и
  > удалении и деградируют в in-memory: то же поведение, что уже описано комментарием в
  > `i18n.jsx:329`, только теперь единообразно для всех четырёх ключей.

  > **Но «поймать и промолчать» упирается в правило NO FALLBACKS, и здесь нужен явный выбор.**
  > Сегодня при заблокированном хранилище вход **не проходит вообще**: `setToken` стоит внутри
  > try/catch формы (`Login.jsx:19-23`), исключение хранилища попадает в тот же `catch`, что и ошибки
  > API, и пользователь видит сообщение об ошибке. Поведение грубое, но честное. Адаптер, глотающий
  > исключение, даёт обратную крайность: вход проходит, работа идёт, а на F5 сессия исчезает без
  > объяснений — ровно та тихая деградация, которую правило запрещает.
  >
  > Решение: адаптер **не бросает** (белый экран недопустим), но факт не теряется — на первом сбое
  > один `console.warn`, и `sessionStore` выставляет `persistAvailable: false`. Флаг живёт в сторе, а
  > не в комментарии, поэтому его видно и коду, и тесту. Пользовательский баннер «браузер блокирует
  > хранилище, сессия не сохранится» — **вне scope** этого плана: он требует строк в EN и RU и места
  > в layout, то есть отдельной задачи; но флаг для него уже будет готов. Компромисс назван здесь,
  > чтобы он остался решением, а не побочным эффектом фикса.

  > **Устойчивость живёт в одном месте: `frontend/src/stores/safeStorage.js`.** Адаптеров два —

## Phase 4: Язык, тема и подсказки — один persist-стор

**Estimate:** 0.5–1 час

**What changes:**
- `frontend/src/stores/prefsStore.js` — новый, `persist`. `lang`, `theme`, `tzSuggestionDismissed`
  — сохраняются в те же три ключа, что и сегодня (`notes_lang`, `notes_theme`,
  `notes_tz_suggestion_dismissed`), чтобы настройки пользователей пережили обновление. Действия
  `setLang`, `setTheme`, `dismissTzSuggestion`. Побочные эффекты (`<html lang>`, `data-theme`) — в
  подписке на стор, не в компонентах.

  > **Адаптер здесь другой, чем в фазе 3, и это не деталь.** У `persist` ровно один `name` — одна
  > запись в хранилище на стор («`name`: a unique name of the item for your store in the storage»).
  > Три легаси-ключа с голыми значениями в эту модель не ложатся вообще: сессионный адаптер фазы 3
  > умеет одно значение, а здесь нужен **fan-out** — `getItem` собирает состояние из трёх
  > `localStorage.getItem`, `setItem` раскладывает обратно в три, `removeItem` чистит три. Формат
  > каждого ключа остаётся прежним: `ru`, `dark`, `1` — голые строки, а не JSON. Альтернатива —
  > отказаться от `persist` и писать значения в `subscribe` вручную; она проще, но тогда в тестах
  > нет `persist.rehydrate()`, а он нужен, потому что гидратация случается один раз при импорте
  > модуля. Берём fan-out адаптер.

  > **Начальный язык по-прежнему выводится из браузера.** Сегодня `getInitialLang()`
  > (`i18n.jsx:325-334`) при отсутствии сохранённого значения смотрит на `navigator.language` и
  > отдаёт `ru` русскому браузеру. Дефолт стора обязан повторить эту логику: если начальным
  > состоянием просто поставить `'en'`, каждый новый русскоязычный пользователь будет получать
  > английский интерфейс — регрессия, которую заметит только он.

  > **Подписки мало: атрибуты выставляются один раз синхронно при старте.** `subscribe` зовёт
  > колбэк только на изменение, а `main.jsx` сегодня специально дёргает `initTheme()` **до**
  > `createRoot(...).render(...)` — иначе тёмная тема применяется после первого кадра и страница
  > моргает светлым. Замена вызова на одну лишь подписку вернула бы этот FOUC, и точно так же
  > `<html lang>` остался бы английским до первого переключения языка. Порядок: гидратация persist →
  > применить `theme` и `lang` из текущего состояния → подписаться на дальнейшие изменения → render.
- `frontend/src/i18n.jsx` — `LangProvider` и `LangContext` удаляются; `useLang()` остаётся как имя,
  но читает стор. `MESSAGES`, `resolve`, `interpolate` не трогаются.

  > **`useLang()` не имеет права вернуть свежий объект из селектора.** Сегодня хук отдаёт
  > `{ lang, setLang, t }`, и лобовой перенос — `useStore(s => ({ lang: s.lang, setLang: s.setLang,
  > t: … }))` — это ровно тот случай, который v5 наказывает не лишним ререндером, а
  > `Maximum update depth exceeded`: новый объект на каждый рендер, строгое сравнение всегда ложно.
  > Правильная форма: `lang` и `setLang` берутся отдельными селекторами по полю, а `t` собирается
  > через `useMemo` от `lang` (или выносится в чистую `translate(lang, key, vars)` вне React).
  > Возвращаемая форма хука остаётся прежней: `useLang()` зовут 14 файлов, `t(` — 146 раз, и ни
  > одна из этих строк не должна меняться.
- `frontend/src/main.jsx` — обёртка `<LangProvider>` уходит; `initTheme()` заменяется подпиской.
- `frontend/src/theme.js` — сводится к `applyTheme(theme)` и подписке; чтение localStorage уходит в

## Out of scope (явно не делаем)

- **TanStack Query.** Правильный инструмент для серверного состояния и прямая рекомендация research —
  но это вторая зависимость сверх запрошенной и переписывание всех фетчей. Кандидат в «что дальше».
- **UI-рефреш** — отдельный план, отдельная задача.
- **Календарь.** `year`/`month`/`selectedDate` в `Calendar.jsx` никем не разделяются; глобальный
  стор для них — ухудшение, а не переезд.
- **Черновики форм** (`timeDraft`, пароли, поля редактора) остаются в `useState`.
- **Дебаунс поиска.** Сегодня запрос уходит на каждое нажатие клавиши; переезд сохраняет паритет и
  не чинит это попутно — иначе тест «три символа = три запроса» будет проверять новую фичу, а не
  отсутствие регрессии.
- **Обвязка шорткатов через `registerAction`.** Стор позволил бы её убрать: `onNewNote` в
  `App.jsx:79-82` сейчас делает `navigate('/notes')` и через `setTimeout(…, 30)` дёргает колбэк,
  зарегистрированный страницей, — потому что до монтирования `Notes.jsx` вызывать нечего. С
  `notesStore.startCreating()` ни ref-реестра, ни тридцати миллисекунд не нужно. Решение осознанное:
  это отдельная задача про `App.jsx` и `useShortcuts`, она не нужна ни одной из четырёх фаз, и
  тащить её сюда — расширять blast radius ради красоты. Зафиксировано как «что дальше», а не
  забыто.
- **`immer`, `devtools`, `subscribeWithSelector`** — объекты плоские, четыре стора в DevTools не
  нуждаются.
- **Оптимистичные апдейты** — сегодня их нет, и стор сам по себе их не требует.
- ~~**Баннер «браузер блокирует хранилище».**~~ **Сделано** — но не в этих четырёх фазах, а по
  finding'у код-ревью (`code-2026-07-30_15-44-27_zustand-migration-iter1.md`, M3: флаг оказался
  write-only). Предупреждение живёт в карточке напоминаний `Settings.jsx`, строки есть в EN и RU,
  покрыто двумя тестами.

## Risks / Unknowns

- **`Maximum update depth exceeded` на объектных селекторах.** Самая частая поломка v5.
  Митигация: селекторы по одному полю, `useShallow` только там, где объект неизбежен; ловится
  первым же рендер-тестом `Notes.jsx`.
- **Серверные данные в client-state сторе.** Инвалидация ручная: забытый вызов перезагрузки после
  мутации = список расходится с БД молча. Митигация: перезагрузка внутри действия стора, а не в
  компоненте, и тест на каждую мутацию.
- **Контейнер и зависимость.** Анонимный volume `/app/node_modules` означает, что без
  `docker compose build frontend` у любого, кто поднимет стек, импорт zustand упадёт. Митигация:
  сборка внутри фазы 1 и явный пункт в критериях.
- **Persist поверх чужого формата.** Главный тихий риск переезда: дефолтный `createJSONStorage`
  меняет формат хранения, и обновление приложения разлогинивает всех и сбрасывает язык с темой —
  без единой ошибки в консоли. Митигация: собственный `PersistStorage` с голыми значениями и тест,
  который поднимает стор поверх легаси-строки, в фазах 3 и 4.
- **Persist и заблокированное хранилище.** Сегодня картина неровная: `i18n.jsx` и `Settings.jsx`
  ловят исключения (4 места), `theme.js` и `auth.js` — нет. После переезда весь доступ идёт через два
  адаптера, поэтому либо оба устойчивы, либо белый экран у всех, у кого хранилище заблокировано:
  гидратация происходит при импорте модуля, до первого рендера. Митигация: try/catch на чтении,
  записи и удалении в обоих адаптерах плюс юнит-тест с бросающей заглушкой в фазах 3 и 4 —
  **тестом, а не ручной проверкой в приватном окне**, как было записано в первой версии этого плана.
- **Это форк-задание.** Новая зависимость в scaffold, который её не имел, — заметное решение для
  ревьюера; отражается в `SUBMISSION.md` шагом фазы 4, а не остаётся на усмотрение.

## Golden Rule compliance

- ✅ Каждая фаза production-ready: после любой из них приложение работает целиком, а не «частично на
  сторе»
- ✅ Нет stub / MVP / placeholder — установка зависимости и инфраструктура сброса тестов едут внутри
  фазы 1, а не отдельной подготовительной фазой
- ✅ Vertical slices по доменам (заметки, аккаунт, сессия, предпочтения), а не по слоям
  («сначала все сторы, потом все компоненты»)
- ✅ Тесты внутри каждой фазы, отдельной фазы «Tests» нет
- ✅ Нет полировочной фазы в конце; `docs/architecture.md` синкается там, где меняется факт
- ✅ Claude-scale эстимация в часах
